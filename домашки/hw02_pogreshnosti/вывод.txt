Задача 1. Ручной счёт
======================================================================
3.14 ≈ π        Δx = 0.001593   δx = 0.0507 %
2.718 ≈ e       Δx = 0.000282   δx = 0.0104 %
9.8 ≈ 9.81      Δx = 0.010000   δx = 0.1019 %
0.333 ≈ 1/3     Δx = 0.000333   δx = 0.1000 %
Порядок по Δx: ['2.718 ≈ e', '0.333 ≈ 1/3', '3.14 ≈ π', '9.8 ≈ 9.81']
Порядок по δx: ['2.718 ≈ e', '3.14 ≈ π', '0.333 ≈ 1/3', '9.8 ≈ 9.81']
Вывод: лучшее приближение — 2.718 ≈ e (и Δ, и δ минимальны). Порядки по Δx и δx
совпадают не всегда: 0.333 имеет маленькую Δ (0.00033), но число само маленькое,
поэтому δ = 0.1 % — хуже, чем у e. Δ зависит от масштаба числа, δ — нет.

Задача 4. Обратная задача — оценка точного значения
======================================================================
x* ∈ [47.2527; 47.3473]  ≈ [47.25; 47.35]
Пояснение: δ ≤ 0.1 % означает |x − x*| ≤ 0.001·|x*|; отсюда x/(1.001) ≤ x* ≤ x/(0.999).
Упрощённо Δ ≈ 0.001·47.3 = 0.0473, интервал 47.3 ± 0.047.

Задача 5. Порог по абсолютной и относительной ошибке

T =   60 °C: A → Δ ≤ 0.3, B → Δ ≤ 0.30

Задача 8. Округление и banker's rounding
======================================================================
round: [0, 2, 2, 4, 0, -2, -2]
Python округляет .5 к ближайшему ЧЁТНОМУ (banker's rounding, IEEE 754),
чтобы половины уходили вверх и вниз поровну и не копили смещение.
точная сумма   = 5000593.0
«вверх»        = 5500593   сдвиг = +500000.0  (≈ +0.5 на каждое число)
banker's       = 5000662   сдвиг = +69.0
Вывод: «всегда вверх» даёт систематический сдвиг +0.5·N = +500 000 на 10⁶ чисел,
banker's — сдвиг около нуля. В финансах миллионы операций округления, и такой
систематический сдвиг превращается в реальные деньги.

Задача 9. Промежуточное округление — зло
======================================================================
эталон fsum = 5.187377517639621
(а) float       = 5.187377517639621  ΔS = 0.000e+00  δS = 0.000e+00
(б) round(·,3)  = 5.186  ΔS = 1.378e-03  δS = 2.656e-04
сумма (а) совпала с эталоном до последнего бита; ошибка (б) больше
даже половины шага сетки float (ε·S/2 = 5.8e-16) в 2.4e+12 раз
Правило: округлять нужно только окончательный результат; промежуточные значения
держим с полной точностью, иначе ошибки округления каждого слагаемого копятся.

======================================================================
Задача 10. Классика 0.1 + 0.2
======================================================================
0.1 + 0.2 = 0.30000000000000004
== 0.3 : False | isclose: True
Δ = 5.551e-17, δ = 1.850e-16
На пальцах: компьютер хранит числа в двоичной системе. 1/10 в двоичной системе —
бесконечная периодическая дробь (как 1/3 = 0.333… в десятичной), и её приходится
обрезать. Поэтому 0.1 и 0.2 хранятся чуть неточно, и эти крошки дают 0.30000000000000004.

Задача 12. Накопление в цикле — сравнение стратегий
======================================================================
способ                  результат           Δ           δ
цикл           100000.00000133288   1.333e-06   1.333e-11
sum()                    100000.0   0.000e+00   0.000e+00
math.fsum                100000.0   0.000e+00   0.000e+00
Вывод: наивный цикл копит ошибку (~1e-6). sum() в Python ≥ 3.12 использует
компенсированное суммирование и почти точен, а fsum возвращает правильно
округлённую сумму. fsum точнее цикла на много порядков.

======================================================================
Задача 13. Суммирование в правильном порядке
======================================================================
эталон fsum          = 500000000000.00006
(а) малые → большие  = 500000000000.00006  Δ = 0.000e+00
(б) большие → малые  = 500000000000.0  Δ = 6.104e-05
Вывод: когда к сумме ~5e11 прибавляют 1e-10, слагаемое меньше половины шага сетки
float и просто теряется. Если сначала сложить маленькие, они успевают накопиться
(5e-5) и не теряются. Правило: суммировать от малых к большим, а лучше fsum.

======================================================================
Задача 14. Детектор накопления погрешности
======================================================================
итерационно: 2.7181459268248984, эталон: 2.7181459268249255, δ = 9.966e-15
δ > 1e-09: не превышена за 10 000 шагов
δ > 1e-06: не превышена за 10 000 шагов
δ > 0.001: не превышена за 10 000 шагов
Вывод: при умножении относительная ошибка каждого шага (~ε/2) складывается, и
δ растёт с числом шагов (в худшем случае ~n·ε, в среднем медленнее, ~√n·ε).
За 10⁴ шагов она доходит лишь до ~1e-14, поэтому пороги 1e-9 и выше не
достигаются. Но в процессах с миллиардами шагов (симуляции, сложные проценты)
ошибка становится заметной.

======================================================================
Задача 15. Финансы: float vs Decimal
======================================================================
float   = 10000.000000171856   расхождение = 1.71856E-7 руб (1.72e-09 %)
Decimal = 10000.00   расхождение = 0.00 руб
int коп = 1000000 коп = 10000.00 руб, расхождение 0
Вывод: «правильный» результат с точки зрения бухгалтерии — ровно 10 000.00 руб,
его дают Decimal и учёт в целых копейках. float не может точно хранить 0.01,
поэтому сумма уже не равна 10000 ровно: проверка == 10000 не пройдёт, а при
миллиардах операций и больших суммах расхождение дорастает до копеек.
Поэтому деньги хранят в Decimal или в целых копейках (int).

Задача 16. Бонус: мини-исследование среднего
======================================================================
цикл       = 0.5006249366621657     отличие от fsum = +31.5 ε
sum        = 0.5006249366621587     отличие от fsum = +0.0 ε
fsum       = 0.5006249366621587     отличие от fsum = +0.0 ε
numpy.mean = 0.5006249366621587     отличие от fsum = +0.0 ε
Вывод: fsum даёт правильно округлённую сумму и служит эталоном. numpy.mean
использует попарное (pairwise) суммирование: ошибка растёт как log n, поэтому
отличие в пределах нескольких ε, но в общем случае равенство с fsum не гарантировано.
